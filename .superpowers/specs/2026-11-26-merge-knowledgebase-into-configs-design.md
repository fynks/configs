# Design: Merge knowledgebase into configs as the project website

Date: 2026-11-26
Status: proposed

## Intent

The human maintains two GitHub repos: `fynks/knowledgebase` (a VitePress site of
Linux, Windows, browser, Android and tool guides) and `fynks/configs` (the actual
dotfiles/config assets plus a large Arch/EndeavourOS setup script). They want one
repo at `/home/ali/Github/configs`. The knowledgebase VitePress site becomes the
website for the configs repo, all file paths and links are corrected to the
merged repo, the JS toolchain is refreshed (VitePress 2 alpha, latest stable for
everything else, Bun as manager), and the setup script is converted into a
README whose every section is a copyable Markdown code block.

## Goals

- One repo at `/home/ali/Github/configs` containing configs assets, guides, and
  the VitePress site.
- The site is the public face of the configs repo; its nav/sidebar, metadata and
  home page reflect "Configs", not a generic knowledge base.
- Every link that points at a repo asset resolves to a file that exists in
  `fynks/configs` on `main`.
- VitePress pinned to the current alpha (`2.0.0-alpha.21`, npm tag `next`);
  every other direct JS dependency at its latest stable release; `bun` 1.4.5
  is the package manager and produces `bun.lock`.
- `scripts/setup.sh` is deleted. `scripts/README.md` documents all 19 sections
  of the script, each as its own copyable fenced code block.
- `bun run docs:build` succeeds with no broken internal links.

## Non-goals

- The `fynks/knowledgebase` repo is left untouched — locally and on GitHub.
  "Merge into configs" means copying its content into the target repo; deleting
  or archiving the source repo was not requested and is destructive, so no such
  step is taken.
- No artwork redesign. The existing K-branded `logo.svg` and `favicon.svg` are
  reused as-is; only text metadata is rebranded to Configs. New "C" artwork
  would be a separate creative task.
- No CI/deployment workflow changes (the old Netlify link is replaced in the
  README with the repo/site link; hosting itself is out of scope).
- No rewriting of the guide content beyond path/link corrections and the new
  setup-script page.
- No rewriting of the config file contents (`backups/`, `browsers/`) themselves.
- No new features in the setup logic — the README describes the old script
  verbatim rather than improving it.

## Anti-goals

- Shipping broken `raw.githubusercontent.com/fynks/configs/...` links.
- Publishing a stale script that no longer exists in the repo.
- Leaving two competing root READMEs or two package managers.

## Constraints

- Target working directory is exactly `/home/ali/Github/configs`.
- VitePress 2 alpha is not stable; config keys must be verified against the
  installed alpha by actually running a build, not assumed from v1.
- `docs/` is the VitePress source root, so the design spec lives in
  `.superpowers/specs/` to avoid being published as a site page.
- Bun 1.4.5 is already installed and matches the current latest release.

## Approaches

### A. Site at configs repo root (recommended)

Copy knowledgebase's `docs/` (including `.vitepress/` and `public/`) and
`package.json` to the configs repo root, then edit in place. Existing config
assets (`backups/`, `browsers/`) stay where they are. The docs already link to
`raw.githubusercontent.com/fynks/configs/...`, so almost no link rewriting is
needed — only genuinely wrong paths.

Trade-off: one `docs/` root and one `package.json` at the repo root, simple
mental model. Chosen because it preserves the site structure the human asked
to reuse and minimises path churn.

### B. Site in a nested `site/` directory

Keep the VitePress app self-contained under `configs/site/`. Trade-off: clearer
separation between assets and site, but a second package root, rewritten links,
and a redundant nested layout. Not chosen — no benefit for a single-purpose
repo.

### C. No VitePress, fold everything into the root README

Trade-off: simplest possible repo, but discards the site the human explicitly
asked to keep. Rejected.

## Decided how

### File layout in `/home/ali/Github/configs`

```
README.md                      merged root README (replaces readme.md)
package.json                   from knowledgebase, edited
bun.lock                       generated by `bun install`
docs/                          from knowledgebase, edited
  index.md
  browsers.md, git.md, windows.md, jdownloader2.md
  android/index.md
  linux/{Setup,grub,fish,vlc,setup-script}.md
  .vitepress/config.mjs, theme/{index.js,style.css}
  public/{favicon.ico,favicon.svg,images/logo.svg,site.webmanifest}
backups/                       unchanged
browsers/                      unchanged
.gitignore                     merged (node_modules, docs/.vitepress/{dist,cache}, ...)
scripts/README.md              replaces scripts/setup.sh
.superpowers/specs/...         this design doc
```

`docs/.vitepress/cache` and `docs/.vitepress/dist` stay ignored.

### Link and path corrections

- `docs/jdownloader2.md`: `system/backups/jdownloader2_backup.jd2backup` →
  `backups/jdownloader2_backup.jd2backup` (the `system/` prefix does not exist).
- `docs/linux/Setup.md`: the setup-script snippet that clones the repo and runs
  `sudo ./setup.sh` no longer applies. Replace it with a link to the new
  `docs/linux/setup-script.md` page and to `scripts/README.md`.
- Normalise other config-asset links to
  `https://raw.githubusercontent.com/fynks/configs/refs/heads/main/...` where
  they differ (policies.json, u_block_origin_configs.txt, kde-shortcuts.kksrc,
  config.fish, jdownloader2 backup).
- `docs/index.md`: keep "View Source" pointing at `fynks/configs`; retitle and
  retagline to reflect that this is the configs repo's site; add a feature card
  for the setup guide.
- Internal nav links (`/linux/Setup`, `/android`, etc.) already correct; add
  `Arch Setup Script` → `/linux/setup-script`.
- `docs/public/site.webmanifest` currently names the app "KnowledgeBase"/"KB"
  and references two PNG icons that do not exist in `public/`. Rename to
  "Configs"/"Configs", drop the missing PNG entries, and point `icons` at the
  existing `/favicon.svg` (`sizes: any`, `type: image/svg+xml`) so every
  referenced asset exists.

### Toolchain

- `vitepress`: exact `2.0.0-alpha.21`.
- Other direct deps: latest stable at implementation time (`vue` 3.5.46,
  `postcss` 8.5.33 as the alpha's optional peer, if needed for the theme).
- Run `bun install` to generate `bun.lock`; scripts remain `docs:dev`,
  `docs:build`, `docs:preview`.
- Verify with `bun run docs:build`; fix any VitePress 2 config-key changes
  surfaced by the build.

### Script → README

- Delete `scripts/setup.sh`.
- `scripts/README.md` opens with what the guide is and a short usage section,
  then contains one `## <Section name>` per section header found in the old
  script, in order, each with a one-to-three sentence explanation and a single
  ```bash fenced block holding that section's code verbatim so it is directly
  copyable. The two preamble lines above the first marker
  (`#!/usr/bin/env bash` and `set -euo pipefail`) are included at the top of the
  Configuration block so the reconstructed script stays runnable; they do not
  become a 20th section. The 19 sections are: Configuration, Core Functions, UI
  Elements, Cleanup, Validation, Username Detection, Package Management,
  Automatic Setup, Welcome and Help, Main Menu, Setup Functions, Necessary
  Packages, Disable Services, Fish Configuration, Optional Packages, Firefox
  Configuration, Summary, Exit, Main Execution.
- `docs/linux/setup-script.md` is the web version of that README (same
  sections and blocks) and links to `scripts/README.md` on GitHub. Both stay
  in sync because they are generated from the same source in one pass.

### Site config edits

`docs/.vitepress/config.mjs`: title "Fynks Configs", description and og/twitter
metadata updated to the configs repo, apple-mobile-web-app-title updated,
footer message updated, nav/sidebar gain the setup-script entry. Keep local
search, cleanUrls, lastUpdated and the existing brand styling.

### Root README

One `README.md` replaces `readme.md`: what the repo is, link to the live site
and source, quick start (`bun install`, `bun run docs:dev`), repo layout, and a
pointer to `scripts/README.md`.

## What is left to the builder

- Exact heading wording and prose in the generated README pages.
- Whether the alpha needs any extra stable peer installed, decided from the
  build output.
- Any additional broken links discovered while running the build.
